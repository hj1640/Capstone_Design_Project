## 단계와 완료 기준

| 단계 | 작업 | 완료 증거 |
|---|---|---|
| 0 | 현재 소스·Notion·빌드 대조, 실행 확인 | 기준 SHA·자료 상태·검증 결과·누락 목록. 현재 빌드 재현은 미확인 |
| 1 | ID/데이터 구조·API 계약·날짜 의미 정의 | 상품→표준식품→조건별 참고값, 개인 수정→제출→통계 흐름과 예제 |
| 2 | 작은 모델로 모바일 실행 사전 검증 | 실제 기기 tokenizer→벡터 출력, 런타임·시간·메모리 기록 |
| 3 | 상품 DB 검색·표준식품 연결 | 잘린 입력/동일 식품 다상품/다른 식품 혼동/미등록에 대한 처리 |
| 4 | Jaccard와 임베딩 검색 비교 | 상품 Top-k와 식품 Top-1·오확정·확인 요청 비율. 상품 단위로 평가 분할 |
| 5 | 동일 모델 FP32/ONNX/INT8 비교·앱 통합 | 변환 손실·실기기 성능·사용자 확인까지의 실행 기록 |
| 6 | 개인 날짜 수정·서버 제출 | 영속 저장·오프라인 재전송·멱등성·수정/취소·사용자 경계 확인 |
| 7 | 신뢰도 정책·공유 기본값 | N/이상값/가중치 선택 근거, 조건별 통계, 버전 이력·되돌리기 |
| 8 | 전체 검증·발표 | 온라인 주문→검색→수정→통계 실행, 한계와 실측 결과 |

1단계 제안: 안정적인 `foodId`/`productId`/`storageRuleId`, 상품 원문과 검색용 정규화 문자열 분리, 모델/색인/규칙 버전, 사용자 확인 결과를 설계한다. 모호한 잘린 텍스트에서 상품명을 복원했다고 단정하지 않는다. 후보 상품들이 같은 식품이면 식품 수준으로만 확정할 수 있다.

수정 통계는 포장지 날짜·구매 후 남은 일수·개봉 후 기간·사용자 추정을 구분해야 한다. N·가중치·이상값 기준·통계 방식·호스팅은 아직 미정이며 기본 상수를 채워 넣지 않는다. 수집 전 사용자 식별과 동의·최소 보관 범위도 설계한다.
