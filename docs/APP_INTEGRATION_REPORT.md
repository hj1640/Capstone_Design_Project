# 실제 앱 연결 검토·구현 보고서 — D-050 / D-051

> 후속 결정 D-052: 사용자가 새 Expo 프로젝트로 별도 앱을 만들도록 승인했다. ‘선택 대기’인 아래 내용은 당시 기록이며 최신 앱 배포 방향은 [NEW_EXPO_PROJECT.md](NEW_EXPO_PROJECT.md)를 따른다.

작성 기준: 2026-11-12. 작업 대상은 `hj1640/Capstone_Design_Project`의 React Native / Expo 앱이다. 별도 루트 폴더의 브라우저 시제품은 이 앱이 아니다. 이 보고서와 `APP_DEPLOYMENT.md`가 현재 적용 안내이며, 0~8단계 및 D-050 문서는 당시의 설계·실험 이력으로 보존한다.

## 1. 먼저 알아야 할 현재 결론

**GitHub에 소스를 올리는 것만으로 기존 휴대폰 앱이 바뀌지는 않는다.** 서버를 실행하고, 기존 Expo 프로젝트 식별자와 실제 서버 주소를 넣어 새 APK를 만들고, 휴대폰에 설치해야 한다. 서버 DB가 자동으로 생기거나 기존 APK가 자동 갱신되는 구조는 아니다.

이번 작업은 개인 평균 기능의 앱 코드와 서버 코드를 연결하고, 기기 연결 정보를 보관하며, 전경 복귀·재시도·철회까지 이어지는 코드를 만든 것이다. 실제 Waitress 프로세스와 SQLite, 앱의 순수 TypeScript 로직을 사용한 검증을 제공한다. **공개 서버 가동, 기존 Expo 서명으로 APK 생성, 실기기 인수는 아직 완료하지 않았다.** 정확한 실행 결과는 [DEPLOYMENT_RESULTS](../benchmarks/DEPLOYMENT_RESULTS.md), 전체 로그·소스 해시는 [JSON](../benchmarks/deployment-verification.json)을 따른다. 검사 파일이 없거나 실패라면 실행 완료로 간주하면 안 된다.

사용자는 “별도 서버는 아직 없음”이라고 답했다. Expo는 처음 로그인 가능하다고 답했으나, 뒤이어 **로그인할 계정 없이 기존 URL만 있다**고 정정했다. 기존 소유자에게 접근 권한을 받는 방법과 새 Expo 프로젝트에 같은 소스를 빌드하는 방법을 설명했으며, 배포 방향 선택이 필요하다. 따라서 남은 일은 **서버 확보·배포 → Expo 접근/앱 식별자 결정 → APK 생성 → 휴대폰 인수**다. 도메인·서버 계정·비용을 임의로 정하거나 결제하지 않았다.

## 2. 사용자가 구현한 기능을 정확히 말하면

“사용자가 포장지에 적힌 소비기한을 확인하여 저장하면, 구매일과의 차이를 그 사용자 자신의 식품별 구매 기록에 반영한다. 서버는 같은 구매 건을 중복 집계하지 않고, 수정하면 이전 값을 교체하며, 철회하면 그 값을 빼서 평균을 갱신한다.”

이는 모든 사람에게 적용하는 공용 소비기한 DB가 아니다. 최신 사용자 선택은 **개인별 평균**이다. 평균은 ‘구매 시점에 포장지 표시일까지 남아 있던 일수’의 기술 통계이며, 안전하게 먹을 수 있는 기간을 실험으로 증명한 수치가 아니다. 평균으로 포장지 날짜를 덮어쓰거나 새 상품의 소비기한을 자동 결정하지 않는다.

예시는 모두 합성 계산 검사용이다. 같은 사용자·식품명·냉장 조건에서 서로 다른 두 구매 건의 차이가 10일과 20일이면 합계 30/건수 2 = 평균 15일이다. 첫 구매의 날짜를 고쳐 12일이 되면 30−10+12 = 32, 평균 16일이다. 두 번째 구매를 철회하면 32−20 = 12, 1건 평균 12일이다. 같은 구매를 여러 번 수정해도 건수는 늘어나지 않는다. 한 번에 두 개를 산 구매도 구매 품목 1건으로 센다. 이 정의는 코드와 시험에 동일하게 적용한다.

## 4. 필터링은 무엇이고, 무엇이 아닌가

최신 개인 평균 경로에는 근거 없는 ‘평균의 절반을 허용폭으로 정한다’, ‘30일은 2.5% 가중치’, ‘서로 다른 N명 이상’ 같은 공용 정책을 적용하지 않는다. 사용자가 개인별 평균을 선택했으므로 N명 조건은 이 기능의 표본 정의와 맞지 않는다. 과거 7단계의 공용 정책 엔진과 합성 실험은 기록으로 남아 있지만 운영 서비스의 해당 경로는 열지 않는다.

현재 검사는 다음과 같다.

| 조건 | 처리 | 이유 / 한계 |
|---|---|---|
| 실제 달력에 없는 날짜, 잘못된 자료형/필드 | 요청 거부 | 계산 자체가 정의되지 않거나 계약에 어긋남 |
| 포장지 출처/날짜 없음 | 평균 제외, 사유 표시 | 사용자 추정과 관찰한 표시일을 섞지 않음 |
| 보관 조건 미정 | 평균 제외, 사유 표시 | 냉장/냉동 기록을 섞지 않음 |
| 포장지 날짜 기록 시 이미 개봉한 품목 | 평균 제외, 사유 표시 | 미개봉 포장 표시일 관측과 다른 조건. 실제 개봉 시각 추적 기능은 아님 |
| 표시일이 구매일보다 앞섬 | 기록은 유지하되 현재 잔여일 평균에서 제외 | 과거 기한 상품 구매 같은 사건을 정상 잔여기간에 섞지 않음. 실제 존재할 수 있는 사건을 ‘거짓’이라고 판단한 것은 아님 |
| 표시일=구매일 | 0일로 포함 | 음수가 아닌 유효한 달력 차이 |
| 사용자 반영 철회 | 기존 기여 제거 | 사용자 선택 및 통계 일관성 |
| 동일 구매 재전송 | 중복 포함하지 않음 | 네트워크 재시도는 새로운 구매가 아님 |
| 매우 긴 정상 형식 날짜 | 임의로 제외하지 않음 | 길이만으로 오류라고 할 실데이터 근거가 없음. 오타/허위 입력을 판별했다는 주장은 하지 않음 |

따라서 **데이터 의미·입력 형식·소유권·중복을 검증하는 필터는 구현되어 있고, 통계적으로 이상한 소비기한을 판별하는 검증된 모델은 없다.** 그 경계를 팀 발표에서도 유지해야 한다. 표본 수를 함께 보여 주지만 ‘몇 건이면 충분히 믿을 수 있는가’는 아직 평가하지 않았다.

## 5. 실제 반례와 디버깅 결과

- 과거 가중 필터에 9, 10, 11, 15, 16을 순서대로 넣는 경우와 거꾸로 넣는 경우의 결과가 달랐다. 기존 실험은 각각 평균 12.2/적격 5건, 약 11.34694/적격 4건으로 공개 여부까지 달라졌다. `check_legacy_counterexample.py`가 이를 재현한다. 현재 개인 경로는 두 순서 모두 12.2가 된다.
- ‘같은 구매 날짜를 다섯 번 고치면 구매 다섯 건으로 세는가?’를 막는다. 기존 기여를 빼고 새 기여를 더하므로 건수는 그대로다.
- ‘서버 저장 성공 후 응답만 사라지면?’은 같은 요청키 재전송으로 복구한다. 연결 코드 발급/등록에도 기기 비밀값을 먼저 영속 저장하여 같은 문제를 처리한다.
- ‘다른 사람의 코드로 기존 구매를 전송하면?’은 서버·계정 바인딩이 달라 전송 전에 차단한다. 다른 사람과 같은 코드를 공유하면 같은 계정이므로 사람마다 별도 코드를 발급해야 한다.
- ‘철회 버튼을 누르는 순간 이전 날짜 전송이 끝나면?’은 매 반복에서 현재 로컬 기록을 다시 읽어 최종 철회까지 처리한다. 조회 중 새 수정이 들어오는 경우도 재실행한다.
- 백업 후 SQLite 연결을 명시적으로 닫지 않으면 Windows에서 백업 파일이 잠기는 오류를 실제 검사에서 발견했다. `contextlib.closing`으로 고쳐 다시 검증한다. 성공 로그만 보고 넘어가지 않고 테스트 종료/정리 오류까지 실패로 처리했다.
- Expo SDK 검사에서 네이티브 패키지 버전 불일치를 발견하여 SDK 권장 버전으로 정렬했다. 추가 peer 버전도 현재 설치된 Expo의 `bundledNativeModules.json` 및 React Native peer 요구를 기준으로 맞춘다. 최신 버전이라는 이유만으로 올리지 않는다.
- 이전 안내의 “eas.json 없음”은 잘못됐다. 파일은 이미 있었으며 개발 APK 프로필이 있었다. 이번에는 독립 실행 preview 프로필을 추가했다. 기존 projectId/package 부재와 실제 빌드 미확인은 별개다.

## 6. 인증·운영의 범위

일반 공개 회원가입·비밀번호 재설정·소셜 로그인은 구현하지 않았다. 이번 시험 배포는 운영자가 개인별 연결 코드를 발급하는 방식이다. 코드는 서버에서 발급한 무작위 값이고, 앱은 256비트 무작위 기기 비밀값을 네이티브 보안 저장소에 보관한다. 서버 DB에는 해시만 저장한다. URL에는 코드를 넣지 않는다. 연결 코드/기기 세션/개인 DB/실제 영수증은 Git에 넣지 않는다.

코드 기본 유효기간 24시간, 세션 기본 30일은 **운영 기본값**이다. 식품 허용폭이나 통계 신뢰도 기준과 관계없다. 서버는 세션 기간을 설정할 수 있고, 운영자는 만료 후 같은 owner ID로 새 코드를 발급한다. 기기 연결 해제는 세션을 폐기하며, 개인 통계의 삭제/철회와 같지 않다.

SQLite는 한 서버 인스턴스의 영구 볼륨에서 사용한다. 다중 서버 복제·대규모 부하·고가용성을 검증하지 않았다. Docker 구성은 Waitress를 내부 포트에 두고 Caddy가 HTTPS를 제공한다. 이 PC에는 Docker/Android SDK가 없어 컨테이너 및 APK 실실행 검증은 남아 있다. 운영 서버에서 DB 백업을 만들고 복원 시험을 해야 한다. 최종 보관 기간·탈퇴 및 전체 삭제 정책은 팀 운영 결정으로 남긴다.

## 7. 기존 데이터 호환성과 남은 기능의 한계

기존 로컬 v1 구매 기록과 사용자 추정 날짜는 읽을 수 있다. 자동으로 포장지 관측으로 변환하지 않으며 평균에 자동 가입시키지 않는다. 과거 시험 서버의 owner ID를 새 서비스 계정으로 몰래 복사하지 않는다. 기존 개발 서버에 이미 묶인 기기는 담당자가 별도 이전 계획을 검토해야 한다. 바인딩을 삭제해 다른 사람의 구매를 전송하는 편법을 쓰지 않는다.

같은 계정의 서버 통계를 새 기기에서 조회할 수 있지만, 전체 냉장고 구매 원본을 새 기기로 내려받는 복원 기능은 없다. 앱 삭제는 로컬 구매 기록을 잃을 수 있다. 같은 package·서명으로 정상 업데이트하고 이전/이후 기록을 실기기로 확인해야 한다.

한 영수증을 나중에 다시 촬영해 신규 등록하면 다른 구매 ID가 생긴다. 요청 중복 방지는 이 의미적 중복까지 감지하지 않는다. 반품/취소 주문·여러 주문이 섞인 캡처·잘린 상품명의 모호성도 별도 실데이터 평가가 필요하다.

실제 1,200 후보/약 600 선별 목록·FoodKeeper XLSX가 없으므로 전체 식품 DB나 정확한 소비기한 추천이 완성됐다고 말할 수 없다. 600은 클래스 수가 아니다. 2층 DB와 MiniLM 비교는 합성/개발 경로의 실험 근거가 있고, 실제 전체 상품 DB와 정상 등록 경로의 자동 소비기한 추천 연결은 별도 남은 작업이다. 양자화의 PC 비교가 휴대폰 속도·정확도를 보장하지 않는다. 구매 예측·실측 소비량도 이번 기능에 포함되지 않는다.

## 8. 무엇을 GitHub에 올리고, 어떻게 적용하는가

`package.json`이 있는 **이 저장소 루트 전체의 추적 소스**를 검토 브랜치로 올린다. 상위 `Capstone Design` 폴더 전체나 과거 브라우저 시제품을 앱 저장소에 덮어쓰지 않는다. 이 브랜치는 원격 main에 없던 0~8단계와 D-050/D-051을 모두 포함하므로 PR 전체 변경을 검토한다.

포함: `src/`, `server/`, `scripts/`, `config/`, `models/`의 manifest, 합성 fixture, `deploy/`, `.github/`, 앱 설정·잠금 파일·의존성 파일, `docs/`, 검토한 `benchmarks/`.

제외: `.env`, `.secrets`, 실제 DB/백업/영수증, 인증 정보, `node_modules`, `.venv`, `.stage0*`, APK, 큰 모델 바이너리. 모델은 제공 스크립트로 준비하고 EAS 빌드에는 필요한 파일을 넣는다. Git 업로드와 EAS 업로드의 제외 규칙이 다른 이유다.

실행 순서와 실제 명령은 [APP_DEPLOYMENT](APP_DEPLOYMENT.md), 팀 공유 문구는 [TEAM_DELIVERY](TEAM_DELIVERY.md), PR 본문은 [PR_APP_INTEGRATION](PR_APP_INTEGRATION.md)이다. 최종 업로드 여부·브랜치 링크·패키지 해시는 별도 전달 상태에 기록하며, 로컬 커밋만으로 GitHub 업로드를 했다고 표현하지 않는다.

## 9. 최종 적용 판정 기준

1. PC 검사 PASS는 개인 평균 로직·HTTP 연결·재시도 프로토콜의 근거다.
2. 실제 HTTPS 서버의 `/healthz` 성공과 DB 재시작/복원 확인이 있어야 서버 적용 완료다.
3. 기존 Expo projectId/package/서명으로 APK 빌드와 설치가 성공해야 앱 배포 가능이다.
4. 실제 지류/쿠팡 이미지, 날짜 수정, 오프라인 재시작, 평균 갱신, 철회까지 휴대폰에서 통과해야 팀 인수 완료다.

현재 코드만 보고 2~4까지 완료라고 판정하지 않는다. 오류가 없음을 보장하는 대신 실행한 범위와 실패·수정·미검증을 남긴다.
