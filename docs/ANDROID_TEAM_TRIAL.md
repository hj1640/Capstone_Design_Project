# 팀 Android 시험 안내 — D-050 / D-051 / D-052

이번 전달물은 기존 팀 앱 소스를 이어 만든 **별도 Android 앱**이다. 계정은 `juuuuuuun`, 프로젝트는 `fridge-app-personal`, 앱 이름은 `스마트 냉장고 개인판`이다. 새 앱의 package는 `com.capstoneteam7.fridge.personal6899818e`다. 이전 `hj1640/fridge-app` 프로젝트나 설치 앱을 삭제할 필요가 없다. 두 앱의 기록을 자동 병합하지는 않는다.

실제 APK 성공 여부·다운로드·소스 커밋은 [클라우드 빌드 기록](../benchmarks/ANDROID_BUILD_RESULTS.md)을 기준으로 확인한다. 이 안내문만으로 설치·실기기 시험 완료를 뜻하지 않는다.

## 이번에 한 일

1. 기존 Expo/React Native 소스의 구매 등록 화면에 지류 영수증과 쿠팡 입력을 연결했다(D-050). OCR 결과의 구매일·식품명·수량은 사람이 확인한다.
2. 포장지 날짜와 구매일을 별도로 보관하고, 개인별·식품명별·보관 조건별 평균 경로를 구현했다(D-050). 평균은 `포장지 날짜 − 구매일`이다. 다른 사람의 값이나 추정 소비일을 섞지 않는다.
3. 등록·수정·재전송·철회에 같은 구매 건을 한 번만 반영하도록 앱과 서버를 구현했다. SQLite 영속 저장, 기기 세션, 전경 자동 재시도와 충돌 안내를 추가했다(D-051).
4. 사용자가 승인한 새 Expo 프로젝트를 실제 생성하고, 기존 앱과 구분되는 Android 식별자와 클라우드 서명키로 빌드를 진행했다(D-052).
5. 실제 첫 빌드에서 드러난 잠금 파일 충돌을 수정했다. 오래된 npm 잠금 파일과 현재 pnpm 잠금 파일의 공존 때문에 EAS가 잘못된 설치 경로를 선택했다. 설치 도구와 버전을 통일했으며 의존성 검사를 건너뛰어 통과시키지 않았다.

| 항목 | 현재 상태 / 의미 |

## 1. Android 팀원이 먼저 확인할 순서

1. 빌드 기록의 **성공한 APK**를 Android 휴대폰에서 내려받아 설치한다. iPhone에는 이 APK를 설치할 수 없다. 앱 이름과 빌드 번호를 기록한다.
2. PC의 Expo 개발 서버를 켜지 않은 상태에서 앱을 연다. 홈과 냉장고 목록에 접근 가능한지 확인한다.
3. 입력 화면에서 **지류 영수증**을 선택하고 비식별 시험 이미지를 인식한다. 구매일·품목명·수량을 수정한 뒤 등록한다. **쿠팡 주문내역**도 별도로 반복한다. 실제 구매 자료를 GitHub에 올리지 않는다.
4. 품목의 **포장지 소비기한** 화면에서 구매일, 표시 날짜, 식품명, 보관 조건을 확인하고 `날짜와 평균 설정 저장`을 누른다. 실제 포장지 확인 없이 임의 날짜를 실제 관측처럼 기록하지 않는다. 계산 시험은 합성 구매로 구분한다.
5. 앱을 완전히 종료했다 다시 열어 구매와 날짜가 유지되는지 확인한다. 비행기 모드에서도 저장·재시작을 반복한다.
6. `내 구매 기록 평균·전송 상태`를 연다. 서버가 없을 때는 **서버 미연결 안내와 전송 대기**가 정상이다. 이 상태에서 평균이 갱신되었다고 보고하지 않는다.

앱이 열리지 않거나 OCR가 실패하면 기종·Android 버전·APK 빌드 ID·실행 순서·오류 문구를 기록한다. 토큰, 연결 코드, 실제 구매 내용은 오류 공유에서 뺀다.

## 2. 서버 평균까지 사용하려면

[서버 배포 절차](APP_DEPLOYMENT.md)의 3절에 따라 별도 서버와 HTTPS 주소를 확보한다. 서버에는 영구 SQLite 볼륨과 개인별 연결 코드 발급 도구가 필요하다. Expo 프로젝트는 이 서버를 대신하지 않는다.

서버 담당자가 `/healthz`의 `status=ok`, `api=personal-v1`, `mode=service` 및 재시작 후 DB 유지 여부를 확인한다. 사용자마다 다른 연결 코드를 발급한다. 앱의 평균 화면에 실제 **HTTPS 서버 주소 + 본인 연결 코드**를 넣는다. 이번 `preview-local` 앱에는 주소 입력 경로가 있어 서버 연결만을 위해 반드시 다시 빌드할 필요는 없다. 앱 네이티브 코드가 바뀌면 새 APK가 필요하다.

연결 후에는 다음 합성 계산 시험을 실행한다. 모두 **같은 개인·같은 식품명·같은 보관 조건**이며 서로 다른 구매 건이다.

| 순서 | 조작 | 기대 결과 |
|---|---|---|
| 1 | 구매일 대비 표시일 차이가 10일/20일인 두 건을 반영 | 합계 30일, 2건, 평균 15일 |
| 2 | 첫 건의 표시일을 바꿔 차이를 12일로 수정 | 합계 32일, 2건, 평균 16일 |
| 3 | 같은 요청을 재시도 | 건수·평균 유지 |
| 4 | 두 번째 구매의 평균 반영 철회 | 합계 12일, 1건, 평균 12일 |
| 5 | 앱·서버 재시작 | 동일한 개인 평균 복원 |
| 6 | 다른 개인이 같은 식품을 등록 | 첫 개인의 평균 불변 |

통신 중단 상태에서 수정→강제 종료→재실행→연결 복구도 시험한다. 서버에 도착하기 전까지 서버의 이전 값이 남는 것은 정상이다. 평균 반영 철회와 기기 서버 연결 해제는 서로 다른 기능이다.

## 3. 필터링을 팀원에게 설명하는 기준

구현한 것은 데이터의 의미·입력 형식·개인 소유권·중복을 확인하는 검사다. 포장지 날짜가 없거나 보관 조건이 미정이거나 기록 당시 개봉된 품목은 평균에서 제외한다. 표시일이 구매일보다 앞선 기록은 보존하되 잔여기간 평균에서 제외한다. 실제 없는 날짜·권한 없는 요청·서로 충돌하는 수정은 거부하거나 충돌로 표시한다.

**긴 기간을 통계적으로 거짓이라고 판단하는 검증된 이상치 필터는 없다.** 이전의 ‘기준의 절반 허용폭’, ‘2.5% 가중치’, ‘최소 N명’은 현재 개인 평균 경로에 적용하지 않는다. 개인 평균은 포장지 날짜나 섭취 안전 판단을 대체하지 않는다. 실제 제품별 분포·오타 라벨이 없는 상태에서 임계값을 검증됐다고 말하지 않는다.

## 4. 팀 공유용 문장

> 기존 앱을 이어 지류/쿠팡 입력, 포장지 날짜 기록, 개인별 구매 잔여일 평균의 앱·서버 코드를 정리했습니다. 수정·철회·중복 재전송 및 서버 재시작은 PC의 실제 HTTP 시험으로 검증했습니다. 새 Expo 프로젝트에서 Android 시험 APK를 만들고 있으며 최종 빌드 상태와 링크는 첨부 기록을 확인해 주세요. 별도 서버는 아직 없어서 현 단계의 APK로는 기기 내 등록·수정을 우선 시험합니다. 서버 구축과 실제 Android 인수 이후에 서버 평균 자동 갱신까지 완료 여부를 판단해야 합니다. 이 평균은 소비 안전 기간을 검증한 값이 아닙니다.

팀원 실제 실행 결과는 [인수표](../benchmarks/DEVICE_ACCEPTANCE_TEMPLATE.md)에 남긴다. GitHub 업로드는 [업로드 안내](GITHUB_UPLOAD.md), 전체 요구·설계·코드·반례는 [상세 보고서](APP_INTEGRATION_REPORT.md)를 따른다.
