# D-050 검토 결과와 설계 근거

## 1. 확인한 실제 대상과 최신 요구

2026-11-12 검토. 실제 앱은 이 저장소의 Expo 57 / React Native 0.86.3 / TypeScript 코드이다. 루트 인수인계의 별도 Python 브라우저 시제품이나 Kotlin 계획을 앱 소스로 오인하지 않았다. GitHub main의 확인된 기준은 `dc385df9babe8bad53064f16674e2019010c4965`; 로컬 0~8단계는 `10058b8`까지의 별도 구현이다. 이 검토 시 원격 main에서 그 이후 팀원 업로드는 발견하지 못했다. 제공된 Expo APK의 소스 커밋은 확인하지 못했다.

사용자 직접 답변을 D-050으로 기록했다.

- 입력: 지류 영수증과 쿠팡 주문내역을 함께 지원. D-002 온라인 전용 범위 대체.
- 수정 날짜: 포장지에 표시된 소비기한. 실제 섭취일/폐기일/개봉 후 기간 아님.
- 평균 범위: 개인별. 기존 공용 통계 설계는 현재 요구가 아님.

실제 1,200 후보/600 선별 파일, FoodKeeper 원본 XLSX는 없다. 600은 고유 식품 클래스 수가 아니다. 상품 7개/식품 5개 합성 카탈로그, 기존 16개 예시 사전, 25개 합성 비교 입력이 실제 전체 DB를 대체하지 않는다. 이 한계를 코드와 문서에서 유지했다.

## 3. 평균의 정확한 의미와 계산

키는 `(인증된 계정 ID, 확인 식품명의 NFKC/공백/소문자 정규화, 보관 조건)`이다. 이름의 동의어를 임의로 모두 통합하지 않는다. 사용자가 동일 식품명을 확인해야 같은 그룹이 된다. 보관 조건은 통계 키로만 분리하며 사용자에게 ‘냉장두부’ 같은 새 식품 클래스를 강요하지 않는다.

각 구매 품목 `i`에 대해 `d_i = 포장지 소비기한 − 구매일`. 날짜 간격은 달력 일수이며 당일 기한은 0일이다. 유효 기여의 `count=n`, `totalDays=S`, `meanDays=S/n`을 저장한다. 식품 개수나 포장 중량으로 가중하지 않는다. 한 구매 품목을 2개 샀다고 독립 관측 2회로 부풀리지 않는다. 서로 다른 포장지 날짜라면 사용자가 품목을 나누어 입력해야 한다.

신규 기여는 `S += d, n += 1`. 수정은 기존 기여를 먼저 빼고 새 기여를 더한다. 이름/보관 조건 변경은 이전 그룹에서 제거 후 새 그룹에 넣는다. 철회는 기존 기여만 뺀다. n=0인 그룹은 삭제한다. 업데이트와 요청키 기록은 같은 SQLite 트랜잭션에 있어 중간 성공이 남지 않는다. 구매 기록 전체를 매번 다시 합산하지 않고 품목과 그룹의 증분 값을 갱신한다.

예: 내 두부 구매 기록 10일·20일 → n=2, 평균15일. 첫 기록을12일로 고침 → n=2, 평균16일. 둘째 구매의 평균 반영 철회 → n=1, 평균12일. 다시 보내도 n이 늘지 않는다. 다른 계정의 기록은 이 계산에 들어가지 않는다.

이 산술평균은 사용자 요구를 명확히 구현하기 위한 **구현 선택**이다. 최근값을 더 중요하게 보는 근거가 없으므로 EWMA/alpha를 도입하지 않았다. 다음 구매일 예측의 산술평균/EWMA 선택은 별개이고 여전히 미정·비활성이다.

## 4. 필터의 기준과 한계

현재 적용하는 것은 의미·형식 검증이다. 이 검증을 ‘식품 안전성 또는 실제 포장지 진위 검증’이라고 주장하지 않는다.

| 입력 상태 | 처리 | 이유/상태 |
|---|---|---|
| 실제 달력에 없는 날짜, 허용하지 않은 필드/자료형 | 서버 422, 집계 안 함 | 형식 불일치. 통계 임계값 아님 |
| 포장지 날짜 없음 | 기록 보관, `LABEL_REQUIRED`, 집계 제외 | 계산 대상 관측이 없음 |
| 보관 조건 미정 | `STORAGE_REQUIRED`, 집계 제외 | 냉장·냉동·실온 기간을 섞지 않기 위함 |
| 개봉 상태 | `UNOPENED_LABEL_ONLY`, 집계 제외 | 미개봉 관측만 비교하기 위한 보수적 설계 선택. 기록 당시 상태를 사용자가 선택하며 실제 개봉시각 자동 추적 아님 |
| 소비기한이 구매일 이전 | 개인 날짜 유지, `EXPIRY_BEFORE_PURCHASE`, 집계 제외 | 구매 시점에 기한이 남은 표본이 아님. 실제 구매가 불가능했다고 단정하지 않음 |
| 당일 기한 | 0일 포함 | 유효한 달력 차이 |
| 평균 반영 끔 | `WITHDRAWN`, 기여 제거 | 사용자 철회 |
| 평균에서 멀지만 형식·의미가 맞는 값 | 같은 가중치 1로 포함 | 거리만으로 오입력이라 판정할 근거 없음. 큰 오타도 통과할 수 있음 |

개인 기록은 최소 N명을 기다리지 않는다. 표본 1개도 기술 통계로 표시하되 구매 건수를 함께 표시한다. 이것이 예측 신뢰도가 충분하다는 뜻은 아니다. 식품명 200자, HTTP 요청 크기, 요청 시간 제한 등은 입력/자원 제약이며 식품 통계 정확도 기준이 아니다.

**기존 필터 반례를 실제 코드로 재현했다.** 합성 기준10일, 편차0.5, 이상값 계수0.1, 최소5명인 기존 공용 정책에 9·10·11·15·16을 순서대로 넣으면 평균12.2/정상기여5/공개 가능. 역순16·15·11·10·9이면 평균 약11.34694/정상기여4/공개 불가. 같은 자료인데 입력 순서가 결과와 공개 여부를 바꾼다. `python server/check_legacy_counterexample.py`가 이 반례를 재현한다. 수치는 실험용이며 실제 소비기한이 아니다. 기존 공용 엔진은 역사·회귀 검사 대상으로 남기고 개인 경로에는 연결하지 않았다. 운영 공용 설정은 계속 disabled다.

또한 실제 포장지에 긴 기간이 표시되는 상품을 ‘평균보다 멀다’는 이유만으로 억제하면 정당한 자료도 버린다. 반대로 포장지 값이라고 입력한 오타/거짓말은 현재 검증만으로 찾아낼 수 없다. 이 한계를 없다고 말하지 않는다. 통계적 이상값 자동 억제를 원하면 실제 라벨·조건·오류 여부가 있는 검증 자료와 허용 오류 비용부터 정해야 한다.

## 5. 정상 사용·재시도·호환성

1. 지류/쿠팡 선택 → 사진 OCR → 이름/구매일/수량 직접 확인 → 등록. 새 품목의 기본 기한은 미정이다. 실제 DB가 없는데 예시 일수를 주지 않는다.
2. 품목 상세 → 포장지 날짜·식품명·보관 조건·기록 당시 개봉 여부 입력 (잘못된 구매일도 정정 가능) → ‘내 평균 반영’ 선택 → 저장. SQLite 기록 저장이 성공한 뒤 완료를 표시한다.
3. 홈의 ‘내 구매 기록 평균·전송 상태’에서 팀 시험 서버와 개인 토큰 연결. 서버가 인증한 owner를 사용한다. 같은 토큰을 여러 사람이 공유하면 개인을 구분할 수 없으므로 **사람마다 별도 owner와 토큰**을 배정해야 한다.
4. 연결된 동안 수정 저장/앱 전면 복귀 시 전송을 시도한다. 연결/재시도 버튼으로도 전송한다. 앱 종료 상태의 백그라운드 전송은 없다. 토큰은 메모리에만 있어 완전 재시작 후 같은 계정으로 다시 연결한다.
5. 전송 전 요청 내용을 고정해 저장한다. 응답이 유실되면 같은 키·같은 내용으로 재시도한다. 그 사이 새 수정/철회가 있으면 먼저 기존 응답을 확인한 뒤 최신 상태를 이어서 전송한다. 429 Retry-After를 존중한다.
6. 다른 기기가 같은 품목을 바꾸면 revision 충돌로 멈추고 사용자가 이 기기의 값을 다시 반영할 때만 재시도한다. 자동으로 서버/로컬 중 하나를 덮어쓰지 않는다. 기록 전체의 다중 기기 다운로드/계정 전환은 구현하지 않았다.
7. 평균 반영을 끄고 저장하거나 평균 화면의 철회 버튼을 누른다. 서버 반영 전에는 ‘전송 대기’, 완료하면 철회 완료를 표시한다. 소비 완료로 품목을 숨기는 것은 과거 구매 관측을 지우는 일이 아니므로 자동 철회하지 않는다. 숨긴 품목도 평균 화면에서 철회할 수 있다.

v1 키 `expiry-feedback-v1`과 기존 기록은 유지한다. `personalAverage`가 없는 이전 기록은 자동 제출하지 않는다. 기존 개인 날짜를 ‘실제 라벨’로 재해석하지 않는다. 새 동기화 상태는 `personal-average-sync-v1`; 서버에 별도 personal 테이블을 추가하며 이전 items/feedback/trust 자료를 덮어쓰지 않는다. 기존 계정 바인딩이 있으면 다른 계정/서버로 조용히 옮기지 않는다.

철회는 **평균에서의 제거**이다. 요청 중복 방지 기록과 개인 품목 자체의 삭제/개인정보 삭제 정책까지 구현했다는 뜻은 아니다. 이전 공용 시험 서버에 제출했던 자료는 새 개인 통계로 이관하지 않으며, 그 서버에서 기존 철회 API로 별도 정리해야 한다.

## 6. 적용 판정과 남는 반례

PC에서 새 개인 경로의 실제 HTTP 호출을 검사했다. 테스트 전용 매핑/공개 엔드포인트를 주입하지 않았다. 그래도 Node의 파일 저장 어댑터는 Android SQLite 자체가 아니며 React 화면 터치 검증도 아니다. JS Android bundle 성공은 APK 생성/설치가 아니다.

팀 시험 후보로 전달 가능하다. **즉시 운영 가능한 최종 서비스라고 판정하지 않는다.** 남는 항목:

- 실제 종이 영수증/쿠팡 이미지, 멀티라인 상품명/수량/취소·반품·여러 주문을 섞은 화면 평가. 현재 파서는 제한된 줄 형식이며 자동 완전 복원을 보장하지 않는다.
- 같은 영수증을 다른 등록 세션에서 다시 넣으면 별도 구매가 된다. 버튼 중복은 막지만 이미지/주문 ID 기반 중복 구매 탐지는 아직 없다. 자동으로 같은 날짜·이름을 지우면 정당한 재구매도 사라지므로 임의 병합하지 않았다.
- 실제 선별 상품→표준 식품→보관 참고 규칙 연결. MiniLM은 아직 개발용 확인/합성 평가 경로다. 개인 평균 기능이 모델의 분류 정확성을 검증해 주지는 않는다.
- 다른 제조 형태·포장 상품을 같은 식품명으로 합치면 분포가 넓어질 수 있다. 현재 평균은 설명용이며 새 품목의 소비기한으로 자동 사용하지 않는다.
- 실제 개인 계정 인증, HTTPS 운영 서버, 백업/모니터링/삭제 정책, 기존 Expo projectId·Android package·빌드 설정, 네이티브 호환성 확인.
- 교수님용 실제 다음 구매일 MAE/변수 효과/모델 비교는 실제 구매 시계열 없이는 완료 불가. 기존 합성 실험을 실측 소비 오차라고 부르지 않는다.

관련 기술 API는 버전에 맞춰 확인했다: [Expo 57 SQLite](https://docs.expo.dev/versions/v57.0.0/sdk/sqlite/), [Expo 57 Asset](https://docs.expo.dev/versions/v57.0.0/sdk/asset/), [React Native AppState](https://reactnative.dev/docs/0.86/appstate). 실제 기기 검증을 대신하지 않는다.
